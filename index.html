01建立直觉 / 入门

什么是大数据？先承认它不是一个技术名词

大数据描述的是一种失衡：数据的体量与增速，超过了单机（一台机器、一个数据库、一块硬盘） 能存储与计算的上限。于是你只剩两条路——造一台超级机器，或者把一千台普通机器组织起来。 整个大数据技术栈，都是第二条路的工程副产品。

三条分界线

  • 容量线：单盘最大十几 TB，单机磁盘位有限；数据到了 PB 级就必须横向切分。
  • 吞吐线：单机读盘 ~200 MB/s，1 TB 数据要读一个多小时；只有并行才能把墙钟时间压下去。
  • 故障线：单机年故障率 2% 看似很低，但一万台集群平均每天就有半台在坏——故障成为常态，而不是异常。

一句话记住分布式

分布式系统 = 分片（把数据切开）+ 副本（把风险摊开）+ 调度（把计算搬到数据旁边） + 协调（让所有人对"现在是什么"达成一致）。你后面看到的 HDFS、MapReduce、Kafka、Flink， 都只是这四件事的不同配比。

实验台 01

数据量尺：从一条短信，到全人类一年的数据

拖动滑块，看量级以 10 倍为单位跳跃。注意你的直觉会在哪里失准。

1TB

常见误区

"数据量大 = 大数据"是错的。一张 1 TB 的 Excel 打不开，是工具问题；一个每天 50 GB、 但要按用户-秒粒度做实时归因的场景，才是大数据问题——规模只是触发器，实时性与多样性才是放大器。

先记住这个数字

把 1 PB 想成 1000 块 1 TB 硬盘。任何"把数据拉到一个地方再算"的想法，在 PB 级都会立刻死在网络带宽上。 这就是为什么大数据的第一原则是：移动计算，不移动数据。

02建立直觉 / 入门

5V：五个互相拉扯的约束，而不是五句赞美

Volume（体量）、Velocity（速度）、Variety（多样）、Veracity（真实）、Value（价值）—— 背下来只要一分钟，难的是看懂它们之间的零和关系：要更快，往往要牺牲一致性； 要更杂，往往要牺牲建模效率；要更真，就要付出清洗与校验的算力。

实验台 02

5V 雷达：拖动顶点，看你的场景被推向哪种架构

可以拖雷达上的顶点，也可以拉右侧滑块。右侧会实时给出"最像哪类系统"的判断。

Volume

体量决定存储形态：GB 用单机，TB 用 MPP 数仓，PB 用对象存储 + 数据湖。

Velocity

速度决定计算范式：分钟级用微批，秒级用流式，毫秒级只能预聚合。

Variety

多样决定建模成本：结构化进仓，半/非结构化先进湖，靠 Schema-on-Read 兜住。

Veracity

真实度决定治理投入：脏数据不会让任务失败，只会让报表安静地错。

Value

价值决定项目生死：没人用的数据湖，就是一台昂贵的空调。

第 6 个 V？

有人加 Variability（多变）。本质仍是：约束越多，可选的架构越少。

03建立直觉 / 入门

数据的一生：五段管道，和一个永远存在的瓶颈

采集 → 传输 → 存储 → 计算 → 服务。任何大数据系统都可以画成这五段； 任何一次"系统变慢"，也都能定位到其中一段的容量饱和。 点开每一站，看它的本质、技术选型与典型故障。

实验台 03

管道压力测试：把流量拉满，看谁先堵

拖动流量滑块；点击任意环节查看细节。红色的那一段就是当前的瓶颈。

背压（Backpressure）是朋友的信号

当计算段跟不上，数据会在传输段堆积。健康的系统会把压力反向传导并降速（背压）， 而不是无声地丢数据或把内存撑爆。Kafka 的消费滞后、Flink 的 checkpoint 反压、Spark 的 spill， 本质都是同一条信息：下游比上游慢。

04拆开机制 / 进阶

存储：为什么要把文件切块，还要存三份

HDFS 的两个设计决定，几乎解释了后面所有分布式存储：固定大小的块（默认 128 MB） 与多副本 + 机架感知。块让大文件变成可并行、可寻址的单元；副本让"机器会坏"从灾难变成日常。

实验台 04

HDFS 切块实验室：改一个参数，看元数据与成本怎么变

调整文件大小、块大小、副本数，观察块数、NameNode 元数据、以及真实磁盘占用。

块大小
副本数

小文件问题（面试高频）

HDFS 的元数据常驻 NameNode 内存，每个文件/块约占 150 字节。1 亿个小文件 ≈ 15 GB 堆内存， 且每个 Map 任务只处理几 KB，调度开销远大于计算。解法：合并（Compaction）、 用 ORC/Parquet 打包、或换对象存储 + 表格式（Iceberg/Hudi）把文件数压下来。

HDFS 之后：计算存储分离

对象存储（S3/OSS）把存储做成无限容量、按量计费的服务，计算集群可以随时扩缩。 代价是没有数据本地性、列表操作慢、元数据一致性弱——这也正是 Iceberg、Delta、Hudi 这些"表格式"要补的洞。

05拆开机制 / 进阶

计算：分而治之，以及那个叫 Shuffle 的昂贵真相

MapReduce 的全部智慧只有三句话：把输入切开并行处理（Map）、按 key 把结果重新分发（Shuffle）、 把同一 key 的结果聚合（Reduce）。其中 Shuffle 是唯一必须让数据跨网络移动的一步， 也因此是绝大多数作业慢、倾斜、OOM 的源头。

实验台 05

WordCount 拆解器：一步一步看数据变形

点「下一步」逐阶段推进，或按「自动播放」。也可以改成你自己的句子。

Map 并行度

Spark 到底改良了什么

  • DAG + 惰性求值：连续 map/filter 会融合成一个 Stage，不落盘。
  • 内存优先：中间结果留在内存，省掉 MapReduce 每轮写 HDFS 的开销。
  • 窄依赖 vs 宽依赖：宽依赖（要 shuffle）才是 Stage 边界与故障重算的边界。
  • 但它没有消灭 Shuffle：groupByKey / join / distinct 依然要跨网络重分区。

看到 Shuffle 就要问的三个问题

① 能不能先过滤再 join（谓词下推 / 小表广播）？② key 分布是否均匀（会不会倾斜）？ ③ 能不能用预聚合把参与 shuffle 的数据量先砍掉一半？这三问能解决 80% 的慢作业。

06拆开机制 / 进阶

流处理：无界数据怎么变成有界的答案

流是无限的，而所有聚合都必须有限。于是有了窗口：按时间把无限的流切成一块一块。 再往上一步是水位线（Watermark）：在"等迟到数据"和"按时出结果"之间画一条线。 这是流处理里最难、也最值钱的两个概念。

实验台 06

窗口实验：滚动 / 滑动 / 会话，与一条会吃掉迟到数据的水位线

切换窗口类型，调窗口与步长，看每条事件被分到哪个窗口、聚合结果如何变化。

窗口类型

滚动 Tumbling

窗口首尾相接、不重叠。每条事件恰好属于一个窗口，适合"每分钟订单数"。

滑动 Sliding

窗口可重叠，步长 < 大小。一条事件会进入多个窗口，适合"最近 5 分钟滚动均值"。

会话 Session

按活动间隔切分，长度不固定。适合用户行为会话，天然处理"来了一会儿又走了"。

事件时间 vs 处理时间：一个必须做的选择

按事件时间（数据里自带的时间戳）计算，结果可重放、可回溯，但必须等乱序数据； 按处理时间（机器到达时刻）计算，延迟最低，但重跑结果不同。 水位线就是那句承诺：「我赌 t 之前的事件已经到齐了」——赌错的部分，要么丢弃，要么进侧输出补算。

07拆开机制 / 进阶

CAP：网络分区时，你只有一个选择

一致性（C）、可用性（A）、分区容忍（P）——P 在分布式系统里不是选项，而是事实： 网络一定会断。所以真正的题意是：分区发生的那一刻，你选 C 还是选 A。 把点拖到三角形里，看一个系统会怎么"变形"。

实验台 07

CAP 三角：拖动那个点，然后按下「切断网络」

点可以在三角形内自由拖动。右侧会解释这个位置在分区发生时的行为。也可以直接选一个真实系统。

CAP 之后还有 PACELC

CAP 只描述"分区时"。可现实里分区是少数时间，于是 PACELC 补上： if Partition → A or C；Else → Latency or Consistency。 没有分区时，你依然要在"多等一次复制"和"快一点返回"之间选。这才是日常真正的取舍。

一致性不是开关，是光谱

  • 线性一致：读到的永远是最新写（像单机）。
  • 顺序一致：所有人看到的顺序一致，但不保证实时。
  • 因果一致：有因果关系的操作不乱序（评论不能先于原帖）。
  • 最终一致：停止写入后，副本终将收敛。便宜、快、但会"读到旧值"。
08做出取舍 / 精通

行存 vs 列存：物理布局决定了你能问什么问题

同一张表，行存把一行的字段放在一起，列存把一列的值放在一起。前者擅长"把一条记录完整取出来"（OLTP）， 后者擅长"扫一列做聚合"（OLAP）——因为它只读需要的列，而且同类型数据压缩率极高。 这不是优化技巧，而是存储模型决定访问模式。

实验台 08

查询 IO 对比器：选几列，看两种存储各读多少字节

勾选查询要用的列，打开/关闭过滤条件，比较行存与列存真正读取的数据量。

查询涉及的列
行存 Row-oriented
列存 Column-oriented

列存为什么快（不只是"读得少"）

  • 压缩：同列同类型、局部有序 → 字典编码 / RLE / 位图，常见 4–10 倍压缩。
  • 向量化：按批处理 + SIMD，减少分支与虚函数调用。
  • 跳过：min/max zone map、Bloom filter，整块数据不读。
  • 延迟物化：先算过滤，最后才把需要的列拼成行。

别拿列存做点查

"按 id 取一条订单"这种请求，列存要把每列都读一遍再拼行，比行存慢一个数量级。 这也是为什么真实系统常常行列混布：ClickHouse/Doris 用排序键 + 稀疏索引， HBase/MySQL 承担点查，分析走列存。

09做出取舍 / 精通

数据倾斜：整个集群在等一个分区

8 个任务里 7 个 2 分钟跑完、1 个跑了 40 分钟——总耗时由最慢的那个决定。 倾斜的本质是 key 的分布不均：可能是真实业务（大客户、热门商品）， 也可能是 join 时 key 为 null 全都挤到一起。识别它只需看一个指标：max 与中位数任务耗时的比值。

实验台 09

倾斜模拟器：把长尾拉长，再用"加盐"救回来

拖动倾斜系数；然后点击「加盐 Salting」，观察最慢任务与总耗时如何变化。

Reduce 并行度

五种解法，按代价排序

  1. 先过滤 / 预聚合：把大 key 在 shuffle 前就砍掉，最便宜。
  2. 加盐（两阶段聚合）：给热点 key 加随机后缀打散，再二次聚合。
  3. 广播小表：把 join 变成 map 端广播，彻底避免 shuffle。
  4. 热点隔离：把 Top-N 大 key 单独抽出来走另一条链路。
  5. 引擎自适应：Spark AQE 的 skew join、Flink 的 keyby 重平衡。

先确认它真的是倾斜

任务慢也可能是数据量本来就大（分区裁剪失效）、单条记录过大（一个 JSON 几百 MB）、 或GC / 磁盘 IO 抖动。看 Spark UI 的 Summary Metrics 里 Shuffle Read Size 的 max 与 75 分位——差 10 倍以上，才是倾斜。

10做出取舍 / 精通

架构选型：没有最佳方案，只有约束下的最优解

面试里最难的问题不是"Flink 怎么用"，而是"你为什么选它"。 下面五个问题覆盖了绝大多数真实约束：数据量、延迟、数据形态、一致性要求、团队与成本。 选完，你会拿到一套栈、三条理由，和一条最该警惕的反模式。

实验台 10

架构选型器：五个问题，一套可辩护的答案

每一题选一个最贴近的选项，结果实时更新。可以点「换个场景」快速切换。

反模式 ①

用流处理做全量重算：历史回刷要重放几个月消息，Kafka 不是你家的归档。

反模式 ②

为 10 GB 数据上 Lambda：两套代码 + 两套口径，维护成本远大于收益。

反模式 ③

把数据湖当数据库：没有表格式与 compaction，小文件会让查询慢到怀疑人生。
